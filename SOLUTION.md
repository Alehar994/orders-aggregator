# Решение

## Что сделано

- В модель заказа и таблицу `orders` добавлена фактически оплаченная сумма `amount_paid_kop`.
- Добавлена миграция `002_order_amount_paid.sql`. Для уже сохранённых заказов новое поле заполняется из `amount_kop`, потому что до появления скидок gross и net совпадали.
- Нормализация заказа принимает и проверяет новые поля `discountPercent` и `amountPaid`.
- `daily-totals` теперь возвращает `total`, `gross`, `discount` и `net` для каждого дня, включая дни без оплат.
- Все вычисления по-прежнему выполняются в целых копейках. `total` равен `gross`, `net` суммируется из `amountPaid`, а `discount` вычисляется как `gross - net`.
- Определение локального дня заказа переведено с фиксированного смещения UTC на форматирование каждого момента в IANA-таймзоне клиента.
- Добавлены тесты скидок, перехода на летнее время, исторических заказов и неполного набора новых полей.

## Причина расхождения по `c_7`

У клиента `c_7` таймзона `Europe/Berlin`. Старый код один раз вычислял её UTC-смещение для текущего момента:

```ts
const offset = tzOffsetMinutes(timezone, new Date());
```

Затем это одно смещение применялось ко всем историческим заказам. Однако 29 марта 2026 года Berlin переходит с UTC+1 на UTC+2. Поэтому часть заказов после перехода, созданных между 22:00Z и 23:00Z, старый код оставлял в предыдущем календарном дне.

Например, `2026-03-29T22:40:08Z` в `Europe/Berlin` — это уже `2026-03-30 00:40:08`. При ошибочном фиксированном UTC+1 получилось бы `2026-03-29 23:40:08`.

Сравнение на итоговой БД подтвердило формулировку жалобы: 27 и 28 марта старый и новый gross совпадают, а с момента перехода расходятся. Для 29–31 марта старый код дал бы соответственно `47639`, `52201`, `44064`, правильные значения — `38333`, `59684`, `35401`.

Исправление получает компоненты локальной даты через `Intl.DateTimeFormat` с IANA-таймзоной отдельно для `createdAt` каждого заказа. Так автоматически учитываются DST и исторические правила зоны.

## Что ещё обнаружено

Во внешнем API новые поля появились не у всей истории. В чистом полном sync 1177 из 5030 заказов не содержали ни `discountPercent`, ни `amountPaid`. Если сделать поля безусловно обязательными, эти заказы будут потеряны и старая статистика сломается.

Принято следующее правило совместимости:

- оба поля отсутствуют — это исторический заказ без скидки, поэтому `amountPaid = amount`;
- оба поля присутствуют — значения валидируются и сохраняются;
- присутствует только одно поле — заказ считается невалидным, потому что безопасно восстановить второе значение нельзя.

`amountPaid` выбран источником истины для `net`: именно он описывает фактический платёж. `discountPercent` валидируется, но сумма скидки не пересчитывается из процента, поскольку требование прямо определяет её как `gross - net`, а процентное вычисление может отличаться из-за правил округления платёжной системы.

Также в существующем коде есть потенциальная гонка между отдельными операциями `get` и `save` при одновременной обработке разных версий одного заказа. Для данного задания поведение не менялось, но в production это лучше заменить атомарным upsert с условием `WHERE orders.updated_at < excluded.updated_at` и определением результата по `RETURNING`.

## Допущения

- Отсутствие сразу обоих новых полей означает старый заказ без скидки.
- `amountPaid` не может быть отрицательным или превышать `amount`.
- `discountPercent` допускается в диапазоне от 0 до 100. Числовые строки поддерживаются так же, как уже поддерживались строковые суммы во внешнем API.
- Денежные значения переводятся в копейки существующей функцией `toKop`, то есть без изменения прежнего правила отбрасывания долей копейки.

5. Дополнительно через PostgreSQL проверены UTC-время и локальное время пограничных заказов `c_7` в `Europe/Berlin`.

## Что можно доделать

- Сделать проверку версии заказа атомарной на уровне SQL, чтобы исключить гонку webhook/sync.
- Добавить срок жизни кэша таймзоны клиента на случай её изменения во внешнем API.
- Ограничить максимальную длину диапазона `from..to`, чтобы запрос не мог создать чрезмерно большой ответ.
- Добавить метрики по невалидным входящим заказам с причиной ошибки, не включая чувствительные данные.
